Payloads include numeric fields ending in `_no`. Some are traditional numbers (safe to display). Others are opaque catalog ids (for support traces — not a public API contract).

## Names, slugs, and numbers

Most entities arrive in three forms. They can look redundant — `"pisces"` and `"pisces"` — but they are three different access patterns, and for multi-word values they diverge:

| Form | Example | Use it for |
|---|---|---|
| `*_slug` | `eight_of_diamonds` | **Application logic.** snake_case, no spaces, stable across API layers. Key caches, enums, `switch`/`case`, and URLs on this. |
| `*_name` | `eight of diamonds` | **Display only.** Human-readable; the view layer capitalizes it (`Eight Of Diamonds`), so the exact string can change between layers. Do not match on it. |
| `*_no` | `card_no: 34` | **Support traces.** Opaque catalog id — log it, don't branch on it. |

Rule: **key on the slug, show the name, log the number.** For single-word values (`pisces`) the slug and name happen to be identical, but only the slug is guaranteed stable — build on it.

## Opaque catalog numbers

Fields ending in `_no` (`system_no`, `planet_no`, `element_no`, and similar) are GEOMETRY's opaque catalog and system identifiers. They exist for auditing, tracing, and troubleshooting, and are **not part of the public contract** — do not key caches, foreign keys, or application logic on them. Use names and slugs for durable integrations.

If you hit unexpected results, **include the relevant `_no` values in your report** — they let us reproduce your exact case immediately. See [Support](/support).

## Tradition numbers vs catalog numbers

| Field | Kind | What it means |
|---|---|---|
| `card_no` | **Tradition** | Cosmic deck position, 0–53. Suits run hearts → clubs → diamonds → spades: A♥ = 1 … K♥ = 13, A♣ = 14 … K♣ = 26, A♦ = 27 … K♦ = 39, A♠ = 40 … K♠ = 52. Jokers are **0** and **53**. |
| `tarot_no` | **Tradition** | Standard tarot numbering (GEOMETRY uses **Rider–Waite–Smith–style** English occult suits: cups, wands, pentacles, swords — not Marseille batons/coins, and not the French *jeu de tarot* card game). Majors 0–21; minors continue the sequence. Wire key stays `tarot` / `tarot_no`. |
| `iching_no` | **Tradition** | King Wen hexagram number, 1–64. |
| `atomic_no` | **Tradition** | Periodic table atomic number. Hydrogen = 1. |
| `chakra_no` | **Tradition** | Chakra position, 1–7 (13 in the extended set). |
| `house_no`, `pada_no` | **Tradition** | Astrological house 1–12; nakshatra pada 1–4. |
| `nakshatra_no` | **Tradition** | Standard Vedic order, 1–27. Ashwini = 1 … Revati = 27. |
| `planet_no` | **Catalog** | Opaque body id. **Not** orbital order, Swiss Ephemeris index, or any astronomical numbering — don't infer meaning from the value. Use `planet_name`. |
| `spread_pos` | **Order** | Life-spread display order on `planetary_spread` slots (**1–14**: sun…phoenix). **Not** a catalog `_no` — sort on this; JSON object keys are unordered. See [get_birthdate → Planetary spread](/tools/get-birthdate#planetary-spread). |
| `system_no` | **Catalog** | Registry id for a symbolic system. Not a rank, not an API version. Use the system slug or name. |
| `element_no` | **Catalog** | Element id — see below. |
| `sign_no` | **Catalog** | Position on *that wheel's* own catalog, not a universal zodiac index. Different wheels reuse the same numbers for different signs. Use `sign_name`. |
| `unicard_no` | **Catalog** | Position within one deck's own catalog. Ranges differ per deck, so the same value means different things in different decks. Use `unicard_name`. |
| `geomancy_no` | **Catalog** | Our ordering of the sixteen traditional geomantic figures, 1–16. The figures are traditional; the numbering is GEOMETRY-specific. Use `geomancy_name`. |

Tradition numbers are safe to display and reason about. Catalog numbers should be treated as opaque.

**Tarot (first mention):** In this product, **tarot** means the divinatory 78-card tradition with Rider–Waite–Smith–style suit names on the wire (`cups` / `wands` / `pentacles` / `swords`). That is a deck **lineage / vocabulary** choice — not the same thing as (a) Tarot de Marseille suit language, (b) the French card game *jeu de tarot*, or (c) how majors are *calculated* from a birth date (`tarot_birth_cards.greer` vs `tarot_birth_cards.tarot_school`). Cosmic / cardology birth faces are a separate playing-card spine that maps *to* tarot minors.

## `element_no` means two different things

`element_no` appears in two lanes, and the value is read differently in each:

| Block | Example | Reading |
|---|---|---|
| `periodic_element` | `element_no: 34`, `atomic_no: 34` | Periodic lane — matches the atomic number. |
| `classical_element` | `element_no: 1700`, `element_name: "earth"` | Classical lane — an opaque catalog id. Earth is **not** periodic element 1700. |

Classical elements have no atomic number, so `element_no` is the one key present in both lanes. That is deliberate: `element_no` resolves for any element block, so you never need two code paths. Read it alongside `element_name` and treat the classical values as opaque.

The same applies to the `element_no` returned inside the `celtic_ogham` and `norse_runes` blocks — those are classical elements.

## Glyph fields (`alchemical_symbol` and friends)

Some payloads include rare Unicode glyphs — notably `periodic.alchemical_symbol` on [`get_name`](/tools/get-name) (Unicode Alchemical Symbols U+1F700–U+1F77F, plus classical planetary marks).

Those characters are **correct on the wire**. If a chat-exported JSON shows a water wave, random pictograph, or other lookalike, the **LLM rewritten the glyph** — cards, cipher sums, and element names in that file are usually still fine. Verify with codepoints or re-call the tool. See [FAQ](/faq#llm-unicode-glyphs).

## Year fields and their boundaries

The `lunar`, `yearly`, and `calendar_years` blocks carry cultural year numbers — `year_no`, `hebrew_year_no`, `persian_year_no`, `vedic_year_no`, `chinese_year_no`, and similar.

These are **tradition numbers**, safe to display: Hebrew `5787` is the anno mundi year, Vedic `1948` is Shaka Samvat, Persian `1405` is the Solar Hijri year.

Which year you get depends on where the date falls relative to that system's boundary — and those boundaries are **not all in the same timezone**. Chinese and Vietnamese use CST, Vedic uses IST, Hebrew and Dreamspell are timezone-neutral, and Persian uses GMT rather than Iran's Tehran-local rule.

**Same payload, different family:** `moon_phase.*_anchor_dt`, `season.*_anchor_dt`, and `retrogrades_active.retro_start_dt` / `retro_end_dt` / `cazimi_dt` look identical — bare `YYYY-MM-DD` — but are GMT sky-event days, not civil year windows. If your dates land near a year boundary or disagree with a local almanac by one day, read [When it covers → Calendar boundaries](/coverage#calendar-boundaries) before reconciling against another library.

### Named moons (`moon_phase` — Tool 2)

Deterministic flags and measures from stored AstroPixels/BOSS moon-phase anchors (**GMT**). No interpretive “meaning.” GEOMETRY follows standard NASA/almanac sky rules (full near perigee / apogee, calendar blue moons, total lunar eclipses) — it does **not** invent private slang math.

| Key | Type | Meaning |
|---|---|---|
| `is_full_moon` | bool | Query date is a stored `full_moon` anchor day |
| `is_blue_moon_monthly` | bool | Second full moon in that Gregorian month (**GMT** `phase_dt`) |
| `is_blue_moon_seasonal` | bool | Third of four full moons between consecutive solstice/equinox anchors |
| `is_blood_moon` | bool | Full moon + total lunar eclipse (`eclipse_code` = `lt`) |
| `is_supermoon` | bool | Full moon **and** `earth_moon_distance_km < 360000` (NASA near-perigee; common almanac numeric lock) |
| `is_micromoon` | bool | Full moon **and** `earth_moon_distance_km > 405000` (near apogee; common almanac numeric lock) |
| `earth_moon_distance_km` | int | Earth–Moon distance (km) on the phase-anchor day; `0` if not an anchor |
| `apparent_diameter_arcmin` | number | Apparent lunar diameter (arcmin) on the phase-anchor day; `0` if not an anchor |
| `phase_gmt` | string | Exact phase instant `HH:MM:SS` **GMT**; `"none"` if not an anchor |
| `eclipse_code` | string | `st\|sa\|sh\|sp\|lt\|lp\|ln` or `"none"` |
| `eclipse_type` | string | e.g. `total_lunar`, `partial_solar`, or `"none"` |
| `prev_blue_moon_monthly_dt` | string | Nearest earlier monthly blue moon date, or `"none"` |
| `next_blue_moon_monthly_dt` | string | Nearest later monthly blue moon date, or `"none"` |
| `prev_blood_moon_dt` | string | Nearest earlier blood moon (`lt`) date, or `"none"` |
| `next_blood_moon_dt` | string | Nearest later blood moon date, or `"none"` |

**Supermoon for builders:** NASA describes a full Moon near **perigee** (https://science.nasa.gov/moon/supermoons/). GEOMETRY encodes that with the standard published threshold **distance < 360000 km** (same numeric rule TimeandDate uses). Source column: BOSS `diameter_value` (km; smaller = closer). Apparent size: BOSS `degree_value` → `apparent_diameter_arcmin`. Boundary example: `2018-01-31` is blood + monthly blue at 360199 km → `is_supermoon: false`.

**Micromoon:** full moon **and** distance **> 405000 km**.

Not advertised: atmospheric “red moon,” folklore nicknames (quiet wire field only).

## Zero means "not applicable"

Where a lookup has no match, or a concept does not apply to that date, GEOMETRY returns a typed placeholder rather than `null`:

| Type | Placeholder |
|---|---|
| Numbers | `0` |
| Names and text | `"none"` |
| Symbols, glyphs, emoji | `""` |
| Lists | `[]` |

So `"card_no": 0` alongside `"card_name": "none"` means *no card for this date in this system* — not card number zero. Check for the placeholder, not for `null`.

**One documented exception:** `day_ruler.norse.deity` in [`get_birthdate`](/tools/get-birthdate#day-ruler) is `null` on Saturdays. Old Norse *laugardagr* means "bath day" and carries no deity, so the payload says so rather than inventing one.

Catalog numbers are non-negative. If you ever see a negative value in a `_no` field, that is a bug — please [report it](/support).

## Rule of thumb

Key on **slugs**. Display **names** (and **tradition numbers** where they mean something to your users). Log **catalog numbers** so support can trace your exact case.
